# [HIGH] Recovery seed material is persisted in localStorage

**File:** [`src/core/stores/onboarding/onboarding.store.ts`](https://github.com/pubky/pubky-app/blob/1b29a961c0c756c6e7064def7dac3b63f03915df/src/core/stores/onboarding/onboarding.store.ts#L11-L23) (lines 11, 18, 20, 22, 23)
**Project:** pubky-app
**Severity:** HIGH • **Confidence:** high • **Slug:** `secrets-exposure`

## Owners

**Suggested assignee:** `jovanovicv90@gmail.com` _(via last-committer)_

## Finding

The onboarding Zustand store uses persist() with the default browser storage and partializes secretKey and mnemonic into the persisted onboarding-storage record. Those values are the generated Pubky private key and BIP39 recovery phrase. Tracing the flow shows they are generated by ProfileController.generateSecrets(), used for signup, and only removed when reset()/clearSecrets() is called. The backup route also allows continuing to profile creation without invoking clearSecrets(), so the seed can remain on disk indefinitely until the user explicitly confirms deletion later. Any same-origin script execution, malicious dependency, compromised injected script, or shared-device local storage access can read localStorage['onboarding-storage'] and recover the account.

## Recommendation

Do not persist secretKey or mnemonic in localStorage. Keep onboarding seed material in memory only, clear it immediately after signup/backup, and enforce backup confirmation before leaving the backup step if the seed must remain available. If persistence is unavoidable, use a short-lived storage design with explicit expiry and encryption tied to a user-provided secret, not a key stored in JavaScript-accessible storage.

## Revalidation

**Verdict:** true-positive

The onboarding store wraps its state in Zustand persist without a custom storage, and the installed middleware defaults to window.localStorage. Its partialize function explicitly includes secretKey and mnemonic under the onboarding-storage key. ProfileController.generateSecrets creates the BIP39 mnemonic and derived secret key, then PublicKeyCard triggers that generation during the browser-key onboarding path. useInviteCodeSignUp reads the persisted secretKey for signup and only clears secrets on non-retryable signup failure; successful signup leaves them intact. The backup page offers backup dialogs, but BackupNavigation's Continue button directly routes to onboarding/profile without clearing secrets. DialogConfirmBackup does call clearSecrets, but that is an optional later confirmation path surfaced by AlertBackup rather than a mandatory completion step. Successful profile creation in useProfileForm sets showWelcomeDialog and navigates home; it does not clear secretKey or mnemonic. As a result, a user can finish onboarding with the account seed still present in localStorage indefinitely, where any same-origin script execution, malicious dependency, browser extension with storage access, or shared-device localStorage access can recover the account.
